### 2. 📍 Browser Geolocation API

#### Why localhost isn't enough for some features

The instructor raised an important limitation of local development: some browser APIs only work in a **secure context** — meaning HTTPS or `localhost`. The Geolocation API is the main example.

Most browsers will refuse to give location data if the site is served over plain HTTP (a remote URL without HTTPS). `localhost` is treated as secure, so it works in development — but once you try to test on another device or share a URL, you need HTTPS. This is one reason deploying to a proper hosted URL matters.

#### What the Geolocation API does

The **Geolocation API** lets the browser ask the user for permission to share their physical location — GPS coordinates (latitude, longitude, altitude, accuracy). The browser handles the permission prompt; the code just asks for the data.

**Accuracy depends on the device:**
- **Mobile with GPS chip** — very accurate, within a few metres
- **Desktop/laptop without GPS** — the browser falls back to WiFi triangulation or IP geolocation, which can be off by anywhere from a few blocks to several kilometres. On school computers, the result might point to the ISP's datacenter, not the actual location.

#### Basic usage pattern

```js
// Check that the browser supports it
if (navigator.geolocation) {
  navigator.geolocation.getCurrentPosition(
    (position) => {
      // Success — position object contains coordinates
      const lat = position.coords.latitude
      const lng = position.coords.longitude
      console.log(`Latitude: ${lat}, Longitude: ${lng}`)
    },
    (error) => {
      // Error — user denied, or device doesn't have location
      console.error('Location error:', error)
    }
  )
} else {
  console.log('Geolocation not supported in this browser')
}
```

The `position.coords` object also provides `accuracy` (in metres), `altitude`, and `speed` if available. On a laptop you'll mostly see just latitude and longitude, with a high accuracy number (large circle of uncertainty).

The instructor demonstrated this live — the browser prompted for location access, the student clicked "allow", and coordinates appeared in the console, pointing approximately correctly on a map.

**Why browsers ask for permission:**
Location data is a highly sensitive capability — knowing someone's precise location can be used to stalk or harm them. It's been massively abused in ad tracking. Browsers therefore require explicit user consent every time (unless the user grants permanent permission). This is a good thing.

### 3. 🌐 Static Site Hosting — Where Vue Apps Live

The Vue app built with `npm run dev` runs a development server on your machine — it's not a deployable website yet. To put it on the internet, it needs to be **built** into a set of plain HTML, CSS, and JavaScript files, then **hosted** somewhere.

#### The build step

```bash
npm run build
```

This compiles and bundles the entire Vue application into a `dist/` folder. The result is:
- `dist/index.html` — the entry point
- `dist/assets/` — all JS, CSS, and other assets, **minified**

**What minification does:**
The build process strips out all whitespace, newlines, and comments from the JavaScript and CSS files. The output is a single wall of code that looks unreadable to humans but is functionally identical. The file is much smaller — less data to download, faster load time. The browser doesn't need whitespace; it's purely for human readability in the source.

The instructor pointed out that the minified JS file might be ~110,000 characters in one line — and noted that Facebook Messenger's minified JS is famously enormous. This is how all modern web apps are shipped.

#### What gets deployed

Only the `dist/` folder contents are deployed — not the source files (`src/`), not `node_modules`, not `package.json`. The browser only needs the final compiled output.

#### Free static hosting options

For a static site (one with no server-side code — just HTML, CSS, JS), many free hosting providers exist:

- **Surge.sh** — simple command-line deployment, no account needed initially, gives a random URL
- **GitHub Pages** — free for public repos, your URL is `<username>.github.io/<reponame>`
- **Netlify, Vercel** — popular alternatives with automatic deployment from GitHub

The instructor primarily demonstrated **Surge** for quick manual deployment, then showed **GitHub Pages via GitHub Actions** for automated deployment.

### 4. 🚀 Deploying with Surge

**Surge** is a command-line tool for pushing a folder of static files to a public URL instantly.

```bash
# Run surge from your project root (no global install needed)
npx surge

# It will ask:
# 1. Login/register (email + password — terminal won't echo the password, that's normal)
# 2. Which folder to deploy — point it to ./dist
# 3. What domain to use — accepts a random *.surge.sh domain, or type your own
```

**Terminal password input — a common surprise:**
When you type a password in the terminal, no characters appear — no dots, no asterisks, nothing. This looks like it's not working but it is. The cursor just doesn't move. Type your password and press Enter. To clear and retype, press `Ctrl+C` or use backspace many times.

**The domain:**
Surge generates a random `*.surge.sh` subdomain by default. The instructor noted that some popular/short names might already be taken. If a name is unavailable, just re-run `npx surge` and it will generate a new random one.

**Important limitation — minification is NOT security:**
The instructor made a key point: minifying your JavaScript does not make it secret. Everything in a JavaScript file that runs in the browser is visible to anyone who opens DevTools → Sources. If you embed an API key in your Vue code, it's in the minified JS — anyone can find it. Never put secrets (passwords, private API keys, server access tokens) in frontend JavaScript code.

### 5. ⚙️ GitHub Actions — Automated CI/CD Deployment to GitHub Pages

The main topic of the session: automating the build-and-deploy process so that every time you push to your repository, the site is automatically rebuilt and published to GitHub Pages.

#### What CI/CD means

**CI/CD** stands for Continuous Integration / Continuous Deployment. In simple terms:
- Every time you push a commit, a set of automated steps runs on GitHub's servers
- Those steps can do anything: run tests, lint code, build the app, deploy to a server
- You never have to remember to manually run the build and deploy

#### GitHub Actions basics

GitHub Actions works through **workflow files** — YAML files stored in `.github/workflows/` in your repository. Each file defines a workflow — a set of triggers and jobs.

The file shown in class: `.github/workflows/deploy.yml`

**Key concepts in the workflow file:**

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches:
      - main
  workflow_dispatch:   # also allows manual trigger from GitHub UI

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v3          # check out the repo code
      - uses: actions/setup-node@v3        # install Node.js
        with:
          node-version: 22

      - run: npm install                   # install dependencies
      - run: npm run build                 # build the Vue app (creates dist/)

      - uses: actions/upload-pages-artifact@v2  # package the dist/ folder
        with:
          path: dist

  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    needs: build

    steps:
      - id: deployment
        uses: actions/deploy-pages@v4      # deploy to GitHub Pages
```

**Walking through the key parts:**

| Part | What it does |
|------|-------------|
| `on: push: branches: [main]` | Triggers the workflow every time a commit is pushed to the `main` branch |
| `workflow_dispatch` | Also allows manually triggering the workflow from the GitHub Actions tab |
| `permissions` | Grants the workflow permission to write to GitHub Pages |
| `runs-on: ubuntu-latest` | Each job runs on a fresh Ubuntu Linux virtual machine in GitHub's cloud |
| `actions/checkout@v3` | Clones your repository code into the VM |
| `actions/setup-node@v3` | Installs the specified Node.js version on the VM |
| `npm install` | Installs all project dependencies (`node_modules`) |
| `npm run build` | Runs the Vite build — creates the `dist/` folder |
| `actions/upload-pages-artifact@v2` | Packages the `dist/` folder as a deploy artifact — **`path: dist`** is the key setting |
| `actions/deploy-pages@v4` | Deploys the artifact to GitHub Pages |

**The `path: dist` setting — why it matters:**
If you deploy the entire repo instead of just `dist/`, GitHub Pages would try to serve your source files directly. The browser would see `src/main.js` (which is Vue component imports, useless in a browser without Vite) instead of the compiled output. Only the `dist/` folder contains the browser-ready files.

**The `base` setting in `vite.config.js` — a critical gotcha:**
GitHub Pages serves project repos at `https://username.github.io/repository-name/` — with the repo name as a path prefix. Vue Router and Vite need to know about this prefix. Without it, all asset paths and routes break. You must add:

```js
// vite.config.js
export default defineConfig({
  base: '/your-repo-name/',   // replace with actual repo name
  // ...
})
```

If `base` is missing or set to `'/'`, the deployed site may show a blank page or broken assets.

#### Setting up GitHub Pages

In your repo on GitHub:
1. Go to **Settings** → **Pages**
2. Under "Source", change it from "None" to **"GitHub Actions"**
3. Save

After your first push, the Actions tab in GitHub shows the workflow running. Green checkmarks = success. After the workflow completes, your site is live at `https://username.github.io/repository-name/`.

#### Secrets — never commit credentials

The instructor gave a strong warning about **secrets** in GitHub Actions and in code generally. If a workflow needs to access external services (e.g. an API key for a weather service, or credentials for a deployment target), those must be stored in **GitHub Secrets** — never in the YAML file itself.

GitHub Secrets are stored in the repository settings and referenced in the workflow as `${{ secrets.YOUR_SECRET_NAME }}`. They are never visible in logs.

**Why this matters:**
Automated tools scan public GitHub repositories for exposed credentials constantly. If you accidentally commit an API key to a public repo, it can be found and abused within minutes — sometimes causing serious billing surprises (cloud services often have automatic scanners for this). Never put passwords, tokens, or API keys in source code.
