### 2. 🔍 Search by Name — Passing a Query Parameter to the API

The Rick and Morty API supports filtering by name via a query parameter:
```
https://rickandmortyapi.com/api/character/?name=rick
```

The instructor showed how to wire up an input field to pass this parameter into the existing `fetchCharacters` function.

**Key implementation points:**
- A `ref` holds the current search value: `const search = ref('')`
- The fetch function is updated to conditionally include the `name` param:
  ```js
  const params = {}
  if (search.value) {
    params.name = search.value
  }
  const response = await axios.get('https://rickandmortyapi.com/api/character', { params })
  ```
- When `search.value` is empty, no `name` param is sent — the API returns all characters
- If a value is passed, the API filters to matching names only

**Why guard the empty string:**
Sending `name=` (empty) to the API behaves differently than sending no `name` at all — always guard with an `if (search.value)` check before adding the param. Without this, clearing the search box might not correctly return all characters.

### 3. ⌨️ `@keyup.enter` & `@input` — Triggering the Search

Two event approaches were covered for when to actually fire the search:

**Option 1 — Button + Enter key:**
```html
<input v-model="search" @keyup.enter="fetchCharacters(1)" />
<button @click="fetchCharacters(1)">Search</button>
```
`@keyup.enter` is a Vue shorthand that fires only when the Enter key is released. The instructor noted this is so common in Vue that it has its own dedicated modifier.

**Option 2 — Live search with `@input`:**
```html
<input v-model="search" @input="fetchCharacters(1)" />
```
`@input` fires on every single keystroke — meaning a new API request is made with every character typed. This works, but fires far too many requests.

The instructor noted: pressing a button to search is considered old-fashioned — modern UX expectation is that search results update automatically as you type.

---

### 4. ⏱️ Debounce — Waiting for the User to Finish Typing

The problem with `@input` firing on every keystroke is the flood of API requests. The solution demonstrated was a manual **debounce** using `setTimeout` and `clearTimeout`.

**The pattern:**
```js
let searchTimeout = 0

function onSearchInput() {
  clearTimeout(searchTimeout)
  searchTimeout = setTimeout(() => {
    fetchCharacters(1)
  }, 1000)
}
```

**How it works:**
1. Every time the user types a character, `clearTimeout` cancels the pending timer
2. A new 1000ms timer is started
3. Only when the user stops typing for 1000ms does the timer expire and `fetchCharacters` actually runs

This means if you type "Rick" quickly, only one API request fires — after the last keystroke, not after each one.

**On choosing the delay value:**
1000ms was used for demonstration, but the instructor discussed this in depth:
- Using the **average** typing speed means 50% of users will experience a delay and 50% won't — not a good target
- Using the **slower end** of typing speeds is better — that way most users get their results right when they finish typing
- There is no single correct number; it depends on your user base

> 💡 This pattern is so common it has a name — **debounce** — and is built into many libraries (e.g. Lodash's `_.debounce`). Building it manually from `setTimeout` and `clearTimeout` is a great way to understand how it works under the hood.

### 5. 🎛️ Status Filter Task — Bulma Form Addons & Button Groups

Near the end of the session, the instructor introduced the **homework/practice task**: adding a status filter (Alive / Dead / Unknown) to the Rick and Morty browser.

**The task brief:**
The R&M API also supports filtering by status:
```
https://rickandmortyapi.com/api/character/?status=alive
```
Valid values: `alive`, `dead`, `unknown`

The goal is to add a set of buttons that filter by status — one for each value, styled as a connected button group so they look like a single control.

**Bulma Form Addons:**
The instructor pointed students to the Bulma Form Addons documentation for the connected button group component — buttons that visually join together without gaps between them.

**🔗 Links shared in class:**
| Resource | Description |
|----------|-------------|
| [Bulma Form — Form Addons](https://bulma.io/documentation/form/general/#form-addons) | Bulma's connected/grouped button component |

**Implementation approach:**
- A `status` ref holds the currently selected status (or empty string for "all")
- Three buttons for `alive`, `dead`, `unknown` — styled with `is-selected` / `is-link` class bound dynamically based on which is active
- Clicking a button updates `status.value` and calls `fetchCharacters(1)`
- The status param is added to the API call the same way as the name param

**The instructor's point on combining filters:**
Because both `name` and `status` are added conditionally to the params object, they compose naturally — searching for "Rick" + status "alive" sends both params simultaneously with no extra logic needed.
