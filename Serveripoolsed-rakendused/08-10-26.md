### 1. 🔎 `find()`: one post by its id

The list leaves the body out, so a single post needs its own page, and for that we need
to fetch exactly one row. `DB` got a method that works like `where()`, except the field
is always `id`:

```php
public function find($table, $class, $id) {
    $sql = "SELECT * FROM $table WHERE id=$id";
    // Execute the SQL query
    $result = $this->conn->query($sql);
    $result->setFetchMode(PDO::FETCH_CLASS, $class);
    return $result->fetch();
}
```

The difference is **`fetch()` instead of `fetchAll()`**. The id is the primary key, so
it is unique and there can only be one answer. `fetchAll()` would wrap that one object in
an array for nothing; `fetch()` returns the first row as an object, or `false` if there
is no such row.

`Model` passes it on as a static method, like `all()` and `where()`, so a controller can
just say `Post::find($id)`:

```php
public static function find($id){
    $db = new DB();
    return $db->find(static::$table, static::class, $id);
}
```

### 2. 🔗 Putting the id in the link

How does the view page know *which* post to show? The simplest tool we already have is a
**query parameter**. We do not need a form to make one; we can write it straight into
the link:

```php
<a href="/admin/posts/view?id=<?= $post->id ?>" class="btn btn-info">View</a>
<a href="/admin/posts/edit?id=<?= $post->id ?>" class="btn btn-warning">Edit</a>
<a href="/admin/posts/delete?id=<?= $post->id ?>" class="btn btn-danger">Delete</a>
```

The PHP tag sits right after `id=` and right before the closing quote, with no spaces
around it. Spaces *inside* the tag are fine.

To check a generated link without clicking it, hover over it: the browser shows the
address in the bottom corner. Or right click, Inspect, and read the `href`.

A side experiment: a query string also works together with POST. The form example got
`action="/form?lol=tore"` with `method="POST"`, and the page received both: the fields in
`$_POST` and `lol` in `$_GET`.

### 3. 👁️ The view page

```php
Route::get('/admin/posts/view', [PostsController::class, 'view']);
```

```php
public function view() {
    $post = Post::find($_GET['id']);
    if($post) {
        return view('posts/view', compact('post'));
    }
    echo 404;
}
```

If the post exists, show it; if not, answer 404. The `return` is there only to end the
function, so the 404 line never runs after a successful view.

The page is a table again, but turned sideways: no `<thead>`, one row per field, the
field name in a `<th>` and the value in a `<td>`:

```php
<table class="table table-hover table-striped">

        <tr>

            <td><?= $post->id ?></td>
        </tr>

            <td><?= $post->title ?></td>
        </tr>
        <tr>
            <th>Content</th>

```

(and the same for category, author, created and updated). The editor complains that
`$post` is undefined in the view file. It is right that the file alone does not define
it, but it works as long as the controller passes it in.

### 4. ✏️ The edit form, and where spaces sneak in

`edit()` is almost the same as `view()`, only the view is different. The form is a copy
of the create form with the current values filled in:

```php
<form action="/admin/posts/edit?id=<?= $post->id ?>" method="POST">
    <div class="mb-3">
        <label for="title" class="form-label">Title</label>
        <input value="<?= $post->title ?>" name="title" type="text" class="form-control" id="title" placeholder="Post title">
    </div>
    <div class="mb-3">
        <label for="body" class="form-label">Content</label>
        <textarea name="body" class="form-control" id="body" rows="3"><?= $post->body ?></textarea>
    </div>
```

- An **`<input>`** is prefilled with the **`value`** attribute.
- A **`<textarea>`** has no `value`: its content goes **between the tags**.
- The `action` carries the id too, so the update knows which post it is.

The important detail: **no whitespace between the quote (or the tag) and the PHP tag**.
Everything in there becomes part of the field. If the textarea looks nicer with the PHP
on its own indented line, the form gets that newline and indentation as part of the
body, saving puts it into the database, and the next edit shows the stored spaces *plus*
the new ones. A few saves later there is a kilometre of whitespace in the database. The
textarea is one of the few elements where a line break in the HTML changes the data, so
keep `<textarea ...><?= ... ?></textarea>` on one line.

### 5. 💾 `update()`: one `save()` for both cases

The form posts to the same address it was opened from:

```php
Route::get('/admin/posts/edit', [PostsController::class, 'edit']);
Route::post('/admin/posts/edit', [PostsController::class, 'update']);
```

`update()` finds the post, fills in the new values and saves it, just like `store()`
does with a new one:

```php
public function update(){
    $post = Post::find($_GET['id']);
    if($post) {
        $post->title = $_POST['title'];
        $post->body = $_POST['body'];
        $post->category = $_POST['category'];
        $post->author = $_POST['author'];
        $post->save();
        return redirect('/admin/posts');
    }
    echo 404;
}
```

We could write a separate `update()` method on the model, but saving is saving. It is
nicer if `save()` figures out by itself whether the row already exists. How can it tell?
A new object has **no id yet**, because the database hands out ids. An object that came
from the database has one:

```php
if($this->id) {
    $db->update(static::$table, $fields, $this->id);
} else {
    $db->insert(static::$table, $fields);
}
```

![save](https://api.memegen.link/images/both/INSERT_or_UPDATE~q/save()_checks_the_id.png)

An `UPDATE` looks like `UPDATE table SET field='value', field='value' WHERE id=...`, so
`DB::update` builds the `SET` part in a loop, adding `name='value', ` for every field:

```php
public function update($table, $fields, $id){
    $updateText = '';
    foreach($fields as $name=>$value) {
        $updateText .= "$name='$value', ";
    }
    $updateText = substr($updateText, 0, -2);
    $sql = "UPDATE $table SET $updateText WHERE id=$id";
    $this->conn->exec($sql);
}
```

The loop leaves a comma and a space at the end, which breaks the SQL. No need for
cleverer logic: those two characters are always there, so `substr($text, 0, -2)` simply
cuts them off. A negative length means "up to that many characters before the end".
Dumping the SQL with `dd()` before running it is the quick way to check that it looks
right.

`updated_at` changed by itself after the update: the database takes care of that column.

> Heads-up: same as with `insert()`, the values go straight into the SQL text, and here
> they come from a form.

### 6. 🗑️ Delete, and the name for all of this

```php
Route::get('/admin/posts/delete', [PostsController::class, 'delete']);
```

```php
public function delete() {
    $post = Post::find($_GET['id']);
    if($post) {
       $post->delete();
       return redirect('/admin/posts');
    }
    echo 404;
}
```

The model's `delete()` is **not static**: it deletes *this* object, so it already knows
its own id. `DB::delete` only needs the table and the id:

```php
public function delete() {
    $db = new DB();
    $db->delete(static::$table, $this->id);
}
```

```php
public function delete($table, $id){
    $sql = "DELETE FROM $table WHERE id=$id";
    $this->conn->exec($sql);
}
```

Clicking Delete makes the rows disappear one by one, permanently.

Create, Read, Update, Delete: this set of operations is called **CRUD**. We built it by
hand to see how it works; frameworks come with CRUD generators that write it for you.
Once requests are sent with JavaScript instead of plain links and forms, the HTTP methods
`PUT`, `PATCH` and `DELETE` come into play too, instead of doing everything with GET and
POST.

### 8. 🍪 Cookies

PHP starts from zero on every request: each refresh runs the whole program again and
nothing stays in memory. The database remembers data, but how does the server know
*which* browser is asking? Two tools answer that, and the first is the cookie.

```php
setcookie('mycookie', 'tasty', time() + 60 * 60 * 24 * 30);
dump($_COOKIE);
```

The first refresh showed no cookie, the second one did. The Network tab explains it:

1. The response carries a **`Set-Cookie` header** (a header telling the browser to do
   something, just like `Location` for redirects).
2. The browser **stores** the cookie.
3. From then on, the browser **sends it back with every request** to that site, even if
   the server never sets it again.

`$_COOKIE` shows what the browser *sent*. On the first request it had nothing to send;
the cookie only arrived with the response. Cookies can be viewed and deleted in the
browser's dev tools (Application, Cookies).

**Why not just put the logged in user's id in a cookie?** Because cookies live in the
browser and the user can edit them. Change `userID=1` to `2` and you are someone else.

Cookies are for less important things: a theme, a language choice (remembered even
without logging in), and **A/B testing**. In an A/B test the site has several versions
of a page (layout, colours, order of content), each visitor randomly gets one, and the
cookie keeps you on the same version. Analytics then show which version works best and
that one is kept for everyone. One presidential campaign site ran hundreds of variants;
a streaming service gave viewers of an anthology series different episode orders to see
which order people finished.

The rule: a cookie is **user input**. Never trust it on the server. If only two values
are valid, check for them, and ignore or overwrite anything else.

### 9. 🗝️ Sessions

The second tool uses a cookie too, but differently. `$_SESSION` only exists after the
session has been started:

```php
session_start();
//$_SESSION['secret'] = 'shhhs';
dump($_SESSION);
```

After setting a value once, it stayed there even with the line commented out. In the
browser a new cookie appeared, **`PHPSESSID`**, with a string of characters in it. It is
not the data encrypted: changing the session value did not change the cookie. It is a
**random unique key**. The data itself is stored **on the server**, by default as a file
in the temporary folder named after that key (PHP's own text format for turning values
into text and back). `session_start()` can be configured to store sessions elsewhere,
for example in a database.

Can the user edit this cookie? Yes, but all that does is disconnect them from their
data: a different key points to a different (empty) file, and the old key brings the
data back. The key is 32 hexadecimal characters, so guessing someone else's is hopeless.
Stealing one is the real risk, but the *contents* of a session can never be changed from
the browser.

That is how logging in works: on login, put the user's id into the session; on the next
request, if it is there, load that user; on logout, remove it.

![Sessions](https://api.memegen.link/images/morpheus/What_if_I_told_you/the_session_cookie_is_only_a_random_key.png)

**Lifetime.** By default both the session cookie and our test cookie live until the
browser is fully closed (all windows). After closing everything the browser got a new
session; with the old `PHPSESSID` value pasted back, the old session would return.

A cookie can be given an expiry as the third argument of `setcookie`, and PHP wants it
as a **Unix timestamp** (seconds since 1970), not a date. `time()` gives the current one,
so "30 days from now" is `time() + 60 * 60 * 24 * 30`. Handy numbers: 3600 seconds in an
hour, 86 400 in a day, 2 592 000 in 30 days.

Sites you use daily keep you logged in by pushing the expiry forward on every visit. Log
in once and you stay in as long as you come back within the period; dig out an old
laptop from a drawer and you will find yourself logged out everywhere.

## ✅ Takeaways

1. **`fetch()` for one row, `fetchAll()` for many.** `find()` looks up by the unique id.
2. **Pass the id in the link as a query parameter**, and answer 404 when the post is not
   found.
3. **Prefill inputs with `value` and textareas between the tags**, with no whitespace
   around the PHP tag, or the spaces end up in the database and multiply.
4. **One `save()` for insert and update:** no id means new, an id means it already
   exists.
5. **View, edit, update and delete complete CRUD.**
6. **Cookies are stored in the browser and sent back on every request.** They are user
   input: never trust them.
7. **A session keeps the data on the server** and only a random key in the cookie; that
   is what a login is built on.
8. **Cookie expiry is a Unix timestamp:** `time()` plus the number of seconds.
