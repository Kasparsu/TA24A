### 1. 🚨 A word on the new PHP vulnerability

Before the code: a critical PHP vulnerability had just been made public, one that allows
**remote code execution** and affects a long range of PHP versions. PHP runs a large part
of the internet, so this matters. Patches are out, so the fix is to update. A local
development setup that nobody else can reach is not in much danger, but anything public
(an information site, a WordPress site, a server you rent) must be updated, and if a
hosting provider runs it, make sure they do it. People are already actively exploiting it.

### 2. 🌬️ Installing Laravel Breeze

We want authentication, and Laravel offers several **starter kits** for it. The newer ones
are built around frontend frameworks (React, Vue, Livewire); we want the simple one,
**Breeze** with plain Blade views
(<https://laravel.com/framework/docs/11.x/starter-kits#laravel-breeze>, installation:
<https://laravel.com/framework/docs/11.x/starter-kits#laravel-breeze-installation>):

```bash
composer require laravel/breeze --dev
php artisan breeze:install
```

The installer asks for the stack (**Blade**) and the test framework (Pest). Not because
tests are not useful, we just do not have time for them in this course. We will not keep
Breeze's frontend as it is either: it serves as a reference, and we rebuild it our own way
later.

After `composer run dev` the welcome page has **Log in** and **Register** buttons, and all
of it works: registration lands on a dashboard, there is a profile page (update your info,
change the password, delete the account), logout, and login again. Breeze wrote the routes
for all of this into a separate `routes/auth.php`, pulled in at the end of `web.php`:

```php
Route::middleware('auth')->group(function () {
    Route::get('/profile', [ProfileController::class, 'edit'])->name('profile.edit');
    Route::patch('/profile', [ProfileController::class, 'update'])->name('profile.update');
    Route::delete('/profile', [ProfileController::class, 'destroy'])->name('profile.destroy');
});

require __DIR__.'/auth.php';
```

Inside `auth.php` are the guest routes (`register`, `login`, `forgot-password`,
`reset-password`) and the logged in ones (`verify-email`, `confirm-password`, `logout`).
We come back to how they work later.

**Forgot your password** asks for an email and sends a reset link. But no email arrives,
because `.env` says:

```ini
MAIL_MAILER=log
```

Laravel can be pointed at a real mail service, but for development the "sent" emails are
written into `storage/logs/laravel.log`. Not pretty to read, but the reset link is in there
and it works.

### 3. ⏪ Reverting what Breeze broke

This is why last lesson's clean install was committed first: the Git changes view shows
exactly what Breeze did. A big pile of controllers, request classes, view components,
Blade views and tests, which is fine. But Breeze 2 was written for the older Laravel, and
it moved the project back to **Tailwind 3**, while the fresh Laravel came with Tailwind 4.
So some of its changes get thrown away:

- `package.json` and the lock file: revert. Breeze swapped in old Tailwind packages,
  PostCSS and the forms plugin, which Tailwind 4 does not need.
- `postcss.config.js` and `tailwind.config.js`: delete. Tailwind 4 is configured
  differently, straight from the CSS file.
- `vite.config.js` and `resources/css/app.css`: revert. Breeze had deleted the Tailwind 4
  setup (fonts and plugins) we actually used.

Some of Breeze's views use **Alpine.js** (dropdowns and the like), so that part stays.
Reverting `package.json` removed it, so it is installed again as a package
(`alpinejs` is back in `package.json`), and `resources/js/app.js` starts it:

```js
import Alpine from 'alpinejs';

window.Alpine = Alpine;

Alpine.start();
```

Restart `composer run dev` and check everything still works. It does; the form inputs just
look a little plainer, because the forms plugin that prettied them up is gone.

Should the generated code be committed? Yes. It is not ours, but we will change it, so it
belongs in Git. The trick is to commit it all at once as `Install breeze`: then the
history shows where it came from, and every later change to those files is clearly ours.

### 4. 🎨 Tailwind CSS: a class for everything

Tailwind is a very popular CSS framework, but it works differently from Bootstrap: no
ready made buttons or components. What it has is a **class for practically every CSS
property**: sizes (in steps, percentages, fractions), fonts, font sizes, text colours,
backgrounds and so on. The docs are full of examples (for instance
<https://tailwindcss.com/docs/grid-template-columns>).

Millions of classes, but the final CSS file is small: Tailwind scans the view files and
only puts the classes you actually use into the build.

Why use it instead of plain CSS? The class lists do get long (an extension like **Tailwind
Fold** collapses them in the editor). But:

- it gives fixed scales for spacing, sizes and colours, so the whole site stays
  consistent instead of using a different pixel value everywhere;
- you can prototype and build a custom design very quickly without leaving the HTML.

A test box in the welcome view:

```html
<div class="bg-blue-500 w-50 h-50"></div>
```

Nothing shows up. The styles are built, but the page never loads them. Vite gives the
built file a random generated name, so instead of linking it by hand, the view names the
source file and Laravel works out the rest:

```blade
@vite('resources/css/app.css')
```

Now the blue box appears.

A VS Code tip: the Laravel extension and **PHP Intelephense** do not always get along.
Intelephense can get stuck and hold up the other plugins, so if things go strange, turn
it off.

### 5. 🧭 `PublicController` instead of a closure

The `/` route was a closure straight in `web.php`. Breeze already made controllers, so our
own pages should get one too: a `PublicController` for the public facing pages, just like
in our own framework. A controller can be written by hand, generated from the VS Code
command palette (the Laravel extension has a *make controller* command), or with Artisan:

```bash
php artisan make:controller PublicController
```

Every `make:` command has `--help` with options for generating more code, but we want a
plain empty controller. It extends the base `Controller` and otherwise works exactly like
ours (surprise: our framework was designed after Laravel's). The route becomes an array
of class and method:

```php
Route::get('/', [PublicController::class, 'index']);
Route::get('/buttons', [PublicController::class, 'buttons']);
```

```php
class PublicController extends Controller
{
    public function index() {
        return view('welcome');
    }

    public function buttons() {
        return view('buttons');
    }
}
```

The welcome view was emptied down to a plain HTML page, and a second page, `buttons`, was
added for the exercise, with links between the two (`/buttons` and back to `/`).

### 6. 📦 `container` and `mx-auto`

Content stuck to the left edge of the screen. Bootstrap and other frameworks have a
`container` class that brings content towards the middle, and Tailwind has one too, but
it only sets the width. It does not centre. For that you add automatic horizontal
margins:

```html
<div class="container mx-auto">
    <button>Click me</button>
</div>
```

### 7. 📝 Homework: Bootstrap's primary button in Tailwind

A plain `<button>` in Tailwind is just text: no `btn btn-primary`, no ready made styles.
That is the exercise. Take the **Bootstrap 5 primary button**
(<https://getbootstrap.com/docs/5.3/components/buttons/>) and rebuild it on the `buttons`
page of the blog using only Tailwind classes.

It does not have to be pixel perfect, but the states matter:

- the normal look (colour, padding, rounded corners);
- **hover**, slightly darker;
- **active** (while clicking), darker still;
- **focus**: press Tab to move to the button and Bootstrap shows a ring around it. People
  forget that pages can be navigated with the keyboard; Tailwind has `hover:`,
  `active:` and `focus:` variants for these.

Most of the time will go into finding the right classes in the Tailwind docs, and that is
the point. **Do not ask AI** to do it: it would be done in seconds, but you would not learn
the classes. Due 23.10, details in the Teams assignment.

## ✅ Takeaways

1. **Breeze adds the whole auth flow** (register, login, profile, password reset) with
   `composer require laravel/breeze --dev` and `php artisan breeze:install`.
2. **Commit before you run a generator.** Then Git shows exactly what it changed, and the
   bad parts (Breeze's Tailwind 3 setup) can be reverted file by file.
3. **`MAIL_MAILER=log`** writes outgoing emails into `storage/logs/laravel.log` during
   development.
4. **Tailwind has a class for almost every CSS property** and only ships the ones you use.
   A view needs `@vite('resources/css/app.css')` to load them.
5. **Routes point at controller methods**: `[PublicController::class, 'index']`, with the
   controller made by `php artisan make:controller`.
6. **`container` does not centre in Tailwind**; add `mx-auto`.
