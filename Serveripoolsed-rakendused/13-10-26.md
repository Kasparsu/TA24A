### 1. 📝 The registration form

`registerForm()` only shows a view, so the dump experiments from last time made way for
one line:

```php
public function registerForm() {
    view('auth/register');
}
```

The views live in their own `views/auth/` folder. The form started as a copy of the post
form and got the four fields a user needs:

```php
<form action="/register" method="POST">
    <div class="mb-3">
        <label for="name" class="form-label">Name</label>
        <input name="name" type="text" class="form-control" id="name" placeholder="Name">
    </div>
    <div class="mb-3">
        <label for="email" class="form-label">Email</label>
        <input name="email" type="email" class="form-control" id="email" placeholder="example@cool.yolo">
    </div>
    <div class="mb-3">
        <label for="password" class="form-label">Password</label>
        <input name="password" type="password" class="form-control" id="password">
    </div>
    <div class="mb-3">
        <label for="password_confirm" class="form-label">Confirm Password</label>
        <input name="password_confirm" type="password" class="form-control" id="password_confirm">
    </div>
    <button class="btn btn-primary">Register</button>
</form>
```

`type="email"` lets the browser check the address format, `type="password"` hides what
is typed. The `name`, `id` and `for` stay the same word so everything lines up.

### 2. 👤 Saving the user, and the unique email

The `User` model and its `save()` already existed, so storing a user is the same pattern
as storing a post: `new User()`, fill the fields from `$_POST`, `save()`. The first
version did exactly that and the row appeared in the `users` table.

Registering again with the **same email** blew up with an *Integrity constraint
violation*: the email column is **unique**, so the database refuses a second row with
it. Good that the database guards it, but the user should not see a crash. So before
saving, look for a user with that email, and also compare the two password fields:

```php
public function register() {
    $users = User::where('email', $_POST['email']);
    if($users || $_POST['password'] !== $_POST['password_confirm']){
        return redirect('/register');
    }
    $user = new User();
    $user->name = $_POST['name'];
    $user->email = $_POST['email'];
    $user->password = password_hash($_POST['password'], PASSWORD_BCRYPT);
    $user->save();
    redirect('/login');
}
```

(The `password_hash` line came later in the lesson, see section 8.) There is no way to
show an error message yet, so a failed registration just lands back on the form. A
successful one goes to the login page.

### 3. 🔑 Logging in

The login form is the register form with two fields fewer: no name, no confirmation,
and `action="/login"`.

```php
public function login() {
    $users = User::where('email', $_POST['email']);
    $user = $users ? $users[0] : null;
    if(!$user || !password_verify($_POST['password'], $user->password)) {
        return redirect('/login');
    }
    $_SESSION['userID'] = $user->id;
    redirect('/');
}
```

- `where()` always returns an **array**: our code does not know the email is unique. So
  take the first element if there is one, otherwise `null`.
- No such user, or a wrong password: back to the login form.
- Otherwise, the one small thing that *is* the login: **the user's id goes into the
  session**, and the user is sent to the front page.

The session is needed on every request, so `session_start()` moved out of the controller
into `public/index.php`, before the helpers and routes (helpers may need the session
too):

```php
session_start();

require __DIR__ . '/../helpers.php';
require __DIR__ . '/../routes.php';
```

### 4. 🧭 `auth()` and a dropdown in the menu

After logging in, nothing on the page showed it. A helper makes the logged in user easy
to reach from anywhere:

```php
function auth(){
    $userID = $_SESSION['userID'] ?? null;
    if($userID) {
        return User::find($userID);
    }
    return false;
}
```

`??` gives the left side if it is set, otherwise the right side, so a visitor without a
session gets `null` instead of a warning. (`helpers.php` needs `use App\Models\User;`.)

The nav now asks `auth()`: logged in users see a Bootstrap **dropdown** with their name
(<https://getbootstrap.com/docs/5.3/components/dropdowns/#single-button>), everyone
else sees Sign up and Login:

```php
<?php if (auth()): ?>
    <div class="dropdown">
        <button class="btn btn-secondary dropdown-toggle" type="button" data-bs-toggle="dropdown" aria-expanded="false">
            <?= auth()->name ?>
        </button>
        <ul class="dropdown-menu">
            <li><a class="dropdown-item" href="/logout">Logout</a></li>
        </ul>
    </div>
<?php else: ?>
    <a class="btn btn-sm btn-outline-secondary" href="/register">Sign up</a>
    <a class="btn btn-sm btn-outline-primary" href="/login">Login</a>
<?php endif ?>
```

Logout is the simplest action of all: remove the id from the session and go home.

```php
public function logout() {
    unset($_SESSION['userID']);
    redirect('/');
}
```

### 5. 😱 Why plain text passwords are a disaster

The login worked, with the passwords stored exactly as typed. Even if the database
itself is well protected, data leaks happen: a bug, a misconfigured server, a backup in
the wrong place. Whoever gets the table gets every user's email *and* password.

And people reuse passwords. With your email and the one password you use everywhere,
the first place to try is your email account, and from there almost everything else can
be reset. Password rules do not help as much as they seem to: asked for a capital, a
number and a symbol, most people capitalise the first letter and add `1!` at the end.

![Plain text](https://api.memegen.link/images/disastergirl/Database_leaked/Passwords_were_stored_as_plain_text.png)

### 6. #️⃣ Hashing: MD5

The answer is to store a **hash** of the password. MD5 was used for this for a long time
and shows the idea well (<https://www.md5hashgenerator.com/>):

- The same input **always** gives the same hash.
- Change one letter and the hash is **completely different**.
- It is **one-way**: there is no formula to turn the hash back into the password.
  Multiplying numbers is easy; given only the product, finding the exact numbers you
  started from is not.

So registration stores the hash, and login hashes what the user typed and compares the
two hashes. If they match, it was the same password. A leaked table shows only hashes.

### 7. 💥 How MD5 gets cracked anyway

There is no shortcut back, but there are tools that try a lot of guesses very fast.
**hashcat** (<https://hashcat.net/hashcat/>) is free and handles MD5, the SHA family,
Wi-Fi passwords, zip and 7-Zip archives, password manager vaults and much more.

Three attacks:

- **Brute force.** Give it the hash and a mask of characters, with increment from 1 up
  to 12 characters. A five-letter password from the class fell in **under 20 seconds**,
  after about 573 million tries, on a school laptop. Six to eight characters take longer
  (a lunch break), and several machines or a decent GPU split the work.
- **Dictionary (wordlist).** Try the most popular passwords first. The famous one is
  **rockyou.txt** (<https://weakpass.com/wordlists/rockyou.txt>): about 14 million real
  passwords from a breach of the company RockYou, sorted by popularity. It is a 103 MB
  text file; open it in Notepad++, not in a normal editor. `123456` and friends are at the
  top, and the list is full of names, hobbies and things people love. Checking 14 million
  hashes is nothing compared to the half a billion tries above. There are bigger lists
  too, including other languages.
- **Lookup tables (rainbow tables).** Since around 2000 people have been computing MD5
  hashes for every combination and storing them in databases. Databases exist to find
  things fast, so cracking becomes a lookup: paste the hash, get the password. Public
  ones are hundreds of gigabytes; torrents go into terabytes.

On top of that, the MD5 algorithm stays the same while computers get faster every year.
That is why MD5 is no longer used for passwords.

![rockyou](https://api.memegen.link/images/buzz/password123/password123_everywhere.png)

### 8. 🛡️ bcrypt: `password_hash` and `password_verify`

What is used instead is **bcrypt**. Hash the same word twice and you get a **different
hash every time**: bcrypt adds a random **salt** and stores it inside the hash. That kills
the lookup tables, since nothing can be computed in advance.

It also means login can no longer compare two hashes. PHP has a pair of functions for
this:

```php
$user->password = password_hash($_POST['password'], PASSWORD_BCRYPT);
```

```php
if(!$user || !password_verify($_POST['password'], $user->password)) {
```

`password_verify` takes the plain password and the stored hash and answers true or
false. (The first try had the condition the wrong way round: we redirect when the
passwords do **not** match, hence the `!`.) Existing users had to register again, since
their plain text passwords no longer verify.

The hash also stores a **cost** factor: how many rounds the algorithm runs. Each step up
makes it a lot slower, not just a bit. 12 is normal today, 13 is fine; somewhere around
20 a single hash takes over a minute. The cost slows down every guess of a brute force
attack too, and as computers get faster you simply raise it every few years. PHP's
default cost is fine for now; `password_hash` takes options if you want to change it.

![bcrypt](https://api.memegen.link/images/interesting/I_don't_always_get_the_same_hash_twice/But_when_I_do,_it's_MD5.png)

### 9. 🧂 An extra salt of our own

Brute force still works against weak passwords, so one more trick: add something of our
own to every password before hashing. If the site demands 12 characters and the code adds
more, an attacker who only has the database has to brute force a much longer string.
It can be any text, the user's name and email, or a hash of a secret word:

```php
$user->password = password_hash($_POST['name'] . $_POST['email'] . $_POST['password'] . md5('yolo'), PASSWORD_BCRYPT);
```

and login has to build the exact same string:

```php
if(!$user || !password_verify($_POST['name'] . $_POST['email'] . $_POST['password'] . md5('yolo'), $user->password)) {
```

This only helps while the code stays secret: if the whole server leaks, the recipe leaks
with it. It still raises the bar.

> Heads-up: the login form has no `name` field, so as committed `$_POST['name']` is missing
> at login and the string never matches the one built at registration. Take the name from
> the user found in the database (`$user->name`) instead, or leave the name out of the
> salt.

Side tip from the lesson: the real fix for reused passwords is a password manager, and
good ones are free.

## ✅ Takeaways

1. **Check for an existing email before saving**, or the unique column throws an
   integrity constraint error.
2. **A login is one line: the user's id in `$_SESSION`.** Logout unsets it;
   `session_start()` runs once in `index.php`.
3. **`auth()` returns the logged in user or `false`**, so views can switch between a user
   menu and the Sign up / Login buttons.
4. **Never store passwords as typed.** Leaks happen and people reuse passwords.
5. **MD5 is one-way but fast**: brute force, wordlists like rockyou and lookup tables
   crack it.
6. **Use `password_hash` with bcrypt and `password_verify`.** Random salt per hash, and a
   cost factor you can raise as computers speed up.
7. **An extra salt of your own** makes leaked hashes harder to brute force, as long as
   login builds exactly the same string.
