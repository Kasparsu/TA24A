> turned the copy-pasted page skeletons into one **Blade layout** with an included

### 1. 🧩 Component libraries on top of Tailwind

Rebuilding Bootstrap's primary button by hand meant a long list of classes for every
state. Doing that for every element of a site is not much fun, and there are libraries
that do it for us. Search for "Tailwind components" and a whole family shows up:

- **Flowbite** (<https://flowbite.com/docs/components/buttons/>), with its colours and
  sizes set through variables (<https://flowbite.com/docs/customize/variables/>),
- **FlyonUI** (<https://flyonui.com/docs/components/button/>),
- **HyperUI** (<https://hyperui.dev/components/neobrutalism/buttons/>),
- **Preline** (<https://preline.co/>),
- **DaisyUI** (<https://daisyui.com/>).

They split roughly into two ideas. Some are **copy and paste**: a page of ready examples
written in plain Tailwind classes, nothing to install. Others need **installing as a
Tailwind plugin** and then add their own component classes (built from Tailwind's
values) such as `btn` or `navbar`. Those class names are deliberately close to
Bootstrap's, so anyone who has used Bootstrap feels at home.

The choice for the blog was **DaisyUI**: its big advantage is a much larger set of
ready made themes than most of the others.

A fair question: if the components come from DaisyUI, why keep Tailwind at all? Because
the libraries only offer **components**. There is no grid, no spacing helpers, nothing
for structure. As soon as we want to lay things out, limit a width or tweak the size of
an element, that is Tailwind's job, and many of the library examples use Tailwind classes
themselves.

![Same picture](https://api.memegen.link/images/same/Bootstrap's_btn_btn--primary/DaisyUI's_btn_btn--primary/They're_the_same_class_name.png)

### 2. 🌼 Installing DaisyUI

DaisyUI went in as a dev dependency (the project uses bun, hence the `bun.lock` change):

```json
"devDependencies": {
    "@tailwindcss/vite": "^4.0.0",
    "concurrently": "^10.0.3",
    "daisyui": "^5.7.50",
```

DaisyUI also has a Laravel specific guide, but it boils down to the same thing: register
the plugin at the end of `resources/css/app.css`:

```css
@plugin "daisyui";
```

The quickest way to see that it works is a small button on the welcome page:

```html
<button class="btn btn-primary">Wow DaisyUI</button>
```

### 3. 🧱 A Blade layout with `@extends`, `@yield` and `@section`

We had two pages, `welcome` and `buttons`, and apart from the link and the content they
were identical: the same `<!DOCTYPE>`, `<head>`, `@vite` line and container. In our own
framework we did something similar by splitting the page into two pieces (header and
footer). Blade can do it with **one** file. A new folder `resources/views/partials/` got
`layout.blade.php`, holding everything the pages share, with a named hole where the page
specific part goes:

```blade
<body>
    @include('partials.nav')
    <div class="container mx-auto">
        @yield('content')
    </div>
</body>
```

The name is up to us, but it makes sense to name it after what goes there, so
`content`. The `container mx-auto` wrapper moved into the layout too, so it does not have
to be written on every page. A page is now only the part that differs:

```blade
@extends('partials.layout')
@section('content')
    <button class="btn btn-primary">Wow DaisyUI</button>
@endsection
```

Note the **dot syntax**, `partials.layout` instead of `partials/layout`. A slash also
works, but Laravel prefers dots for paths like this because Windows and Linux use
different directory separators, and dots avoid that problem.

![Layout](https://api.memegen.link/images/officespace/If_every_view_could_just_@extends_the_layout/That_would_be_great.png)

### 4. 🧭 A responsive navbar with `@include`

With the layout in place the old links were gone, so a proper menu was needed. DaisyUI's
navbar page has a variant that collapses on small screens and shows the full menu on
large ones
(<https://daisyui.com/components/navbar/#responsive-collapse-on-small-screen-full-content-on-large-screen>).
It is long, so instead of pasting it into the layout it got its own file,
`partials/nav.blade.php`, and the layout pulls it in with `@include('partials.nav')`
(seen above).

The markup has **two menus**: one for mobile (inside `collapse-content`, `lg:hidden`) and
one for wide screens (`navbar-center hidden lg:flex`). They do not even behave quite the
same, and every link has to be written twice, which is a bit sad but normal for this
kind of component. The placeholder "Item 1" became a link to the buttons page in both
menus, and the logo link leads to the front page:

```blade
<a href="/" class="btn btn-ghost text-xl">daisyUI</a>
...
<li><a href="/buttons">Buttons</a></li>
```

### 5. 🎨 DaisyUI themes

Changing the whole look of the site should not mean picking colours by hand. DaisyUI's
themes page (<https://daisyui.com/docs/themes/>) shows that the plugin line can take
settings. `themes: all` builds every theme into the CSS:

```css
@plugin "daisyui" {
  themes: all;
}
```

and the `data-theme` attribute on `<html>` picks one:

```html
<html lang="en" data-theme="cyberpunk">
```

The themes page lists all the names, and there is a theme generator for making your own
(all the colours are just variables), which is a lot quicker than inventing a palette
from scratch.

![Themes](https://api.memegen.link/images/kombucha/Picking_30_theme_colours_by_hand/themes:_all,_then_data--theme=cyberpunk.png)

### 6. 🏭 Generating the `Post` model with Artisan

To show something meaningful the blog needs content. In our own PHP project we used
**posts**, so that is where to start. A post needs a migration (for the table), a factory
and a seeder (for test data), a model class (to read and hold the rows) and later a
controller. All of that could be written by hand, but `php artisan` has `make:` commands
for every Laravel class, and the generators know what Laravel expects. `make:model` can
even create the related classes in one go with flags, and `-a` (`--all`) makes all of
them:

```bash
php artisan make:model Post -a
```

The model name is singular, `Post`. One command produced eight files: the model, the
controller, `StorePostRequest` and `UpdatePostRequest`, a policy, a factory, a migration
and a seeder. The model itself is tiny:

```php
class Post extends Model
{
    /** @use HasFactory<\Database\Factories\PostFactory> */
    use HasFactory;
}
```

It is good practice to **commit generated code straight away**, as its own commit. It is
our code now and we may change it, but we did not write it, and a separate commit shows
later exactly what we changed ourselves.

### 7. 🗄️ The posts migration: `id`, `timestamps`, `string`, `nullable`

The migration file name starts with the date and time it was generated, so migrations
always run in order. Laravel already filled in the table name, **`posts`**, plural, even
though we only said `Post`. Laravel has a pluralizer that converts English words between
singular and plural (it would not manage Estonian, so the class names stay English).

The generated migration already had two lines. Ctrl+clicking them opens the Blueprint
code in `vendor/` (read it, never edit it):

- `$table->id()` is a `bigIncrements` column named `id`: an auto incrementing, unsigned
  (only positive) big integer.
- `$table->timestamps()` adds two nullable dates, `created_at` and `updated_at`, which
  Laravel fills in itself. It is possible to have tables without them, but then Laravel
  has to be told so.

A post needs a title and a body:

```php
Schema::create('posts', function (Blueprint $table) {
    $table->id();
    $table->string('title');
    $table->text('body')->nullable();
    $table->timestamps();
});
```

Why `string` when databases have no column type called string? Laravel looks at which
database it is talking to and picks the best real type: for MariaDB a `string` became
`VARCHAR(255)` in DataGrip. It is simply easier to think in terms of "a string" and "a
longer text".

Laravel also **flips the null rule** around. When we built tables by hand, a column could
be empty unless we remembered to forbid it, and it is easy to forget. In Laravel every
column is **NOT NULL by default**, and we have to say explicitly when something may be
empty, with `->nullable()`. It protects us from our own forgetfulness.

### 8. 🔁 `migrate`, `rollback`, `refresh` and `fresh`

`php artisan migrate` runs every migration that has not run yet; DataGrip (after a
refresh) showed the new `posts` table. After adding `nullable()` to `body`, running
`migrate` again only said **"Nothing to migrate"**: that migration had already run. The
`migrate:` subcommands help here:

- `migrate:rollback` undoes the last batch (our posts table disappeared), and `migrate`
  then runs it again with the change.
- `migrate:reset` rolls everything back; `migrate:refresh` does both, all the way down
  and up again.

`refresh` has a catch, because it relies on the `down()` methods. A demo: rename the
table in the migration to `posts2` (both in `up` and `down`) and run `migrate:refresh`.
No error, but DataGrip now has **both** `posts2` and the old `posts`. The `down()` tried
to drop `posts2`, which did not exist yet, and because it is `dropIfExists` it silently
moved on, so the original `posts` table was never dropped.

![Headaches](https://api.memegen.link/images/headaches/migrate:refresh_after_renaming_the_table.png)

The better command while developing is **`migrate:fresh`**: it ignores the `down()`
methods completely, drops **every** table and runs all migrations again. The stray table
was gone.

While the project only lives on your own machine, editing, deleting and re-running
migrations like this is fine. Once there is a **production** system, every database
change needs a **new** migration: dropping a table also drops its data, and users who
just registered would not be pleased to find everything gone.

### 9. 🌱 Factory and seeder: 1000 posts

For test data Artisan made `PostFactory` and `PostSeeder`. The `UserFactory` from last
time already showed the pattern: the `fake()` helper (Faker) fills each database column.

```php
return [
    'title' => fake()->sentence(),
    'body' => fake()->paragraphs(6, true),
];
```

`paragraphs()` has a small trap (as do `sentences()` and `words()`): it returns an
**array** of paragraphs, which cannot go into a text column. The second argument `true`
makes it return one string with the paragraphs joined together.

The seeder then uses the factory, just like the `User::factory(10)` example in
`DatabaseSeeder`:

```php
public function run(): void
{
    Post::factory(1000)->create();
}
```

(with `use App\Models\Post;` at the top). We once typed a couple of posts into the
database by hand; a thousand posts with paragraphs this long would not get done in a day.
`php artisan db:seed --class=PostSeeder` ran it in about three seconds, and the posts
table held 1000 rows.

![Stonks](https://api.memegen.link/images/stonks/Post::factory(1000)--~gcreate()/1000_blog_posts_in_3_seconds.png)

The text is Latin style lorem ipsum. Faker supports locales, and it also has `realText`,
which takes sentences from a public domain book (Alice in Wonderland in English); other
languages can be plugged in as well.

Without `--class`, `db:seed` runs `DatabaseSeeder`, so that is where the post seeder gets
called, keeping the code in its own class:

```php
// User::factory()->create([
//     'name' => 'Test User',
//     'email' => 'test@example.com',
// ]);

$this->call(PostSeeder::class);
```

The test user is commented out for now: running the seeder a second time hit an
**integrity constraint** error, because `test@example.com` already existed and the email
column is unique. Ideally seeders work both on an empty database and on one that already
has data (for example by checking whether the user exists first); that is for later.

Finally, re-seeding after every `migrate:fresh` gets tedious, so the migrate commands
take a `--seed` flag:

```bash
php artisan migrate:fresh --seed
```

All tables dropped, rebuilt, and 1000 fresh posts again. This command will be used a lot,
so it is worth remembering.

## ✅ Takeaways

1. **Component libraries save the class soup**: some are copy and paste, others (like
   DaisyUI) are Tailwind plugins with Bootstrap-like classes such as `btn btn-primary`.
   Tailwind stays for layout and fine tuning.
2. **DaisyUI is one line in `app.css`**: `@plugin "daisyui";`, with `themes: all` and a
   `data-theme` attribute on `<html>` to switch the whole look.
3. **One layout, many pages**: `@yield('content')` in the layout, `@extends` and
   `@section` in the page, `@include` for pieces like the navbar. Use dot paths.
4. **`php artisan make:model Post -a`** generates model, controller, requests, policy,
   factory, migration and seeder. Commit generated code on its own.
5. **Laravel columns are NOT NULL by default**; add `->nullable()` where empty is allowed.
   `string` maps to the right type for the database (VARCHAR(255) in MariaDB).
6. **Use `migrate:fresh` while developing**, not `refresh`, which trusts the `down()`
   methods. In production every change gets a new migration.
7. **`fake()->paragraphs(6, true)`** returns a string, not an array.
   **`php artisan migrate:fresh --seed`** rebuilds the database with test data in seconds.
