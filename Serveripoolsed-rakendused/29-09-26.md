### 1. 🎛️ Controllers

`routes.php` was turning into a file full of page logic: every route carried its own
closure with the page data inside. The usual fix is a **controller**: a class whose public
methods are the actions. The route file goes back to being a list:

```php
use App\Controllers\PublicController;
use App\Router;

Router::addRoute('/', [PublicController::class, 'index']);
Router::addRoute('/us', [PublicController::class, 'us']);
Router::addRoute('/test', [PublicController::class, 'test']);
```

The action is now an array of two strings: the class and the method name.
`PublicController::class` is just the fully qualified class name as a string
(`'App\Controllers\PublicController'`), but written this way the editor checks it and a
rename follows automatically.

Why is this better than closures in `routes.php`? Nothing forces every route into one
controller. An admin panel can get its own controller, login its own `AuthController`, and
each stays small. Meanwhile `routes.php` is still the one place that lists every address
the application answers to.

If you did the Technology page homework, move its route the same way: a `technology()`
method in `PublicController` and one `addRoute` line.

### 2. 🪄 Calling a controller method dynamically

`addRoute` used to accept only a `callable`, so passing an array made PHP complain. The
type became a union:

```php
public static function addRoute(string $path, callable|array $action) {
```

Then `call_user_func` failed: it cannot call a **non-static** method from a class name
alone. We do not want the controller methods to be static (later the controller's
constructor will be a good place for things every action needs), so the dispatcher makes
the object itself:

```php
if(is_callable($match->getAction())) {
    call_user_func($match->getAction());
} else {
    $class = $match->getAction()[0];
    $controller = new $class();
    $method = $match->getAction()[1];
    $controller->$method();
}
```

Both `new $class()` and `$controller->$method()` take their names from variables. It looks
odd, but it works as long as the string is a real class name and a real method name. A
production router would check that (two elements, class exists, method exists); ours
trusts that we put sensible things in.

A common mistake while typing this: taking both the class *and* the method from index
`0`. The method name is at index `1`.

### 3. 🧰 `helpers.php` and a `view()` function

Two problems showed up after the move. The `include __DIR__ . '/views/...'` paths broke,
because `__DIR__` is now the `src/Controllers` folder. And `dump()` was still sitting in
`public/index.php`, where it never belonged.

Plain functions that are not part of any class go into a helpers file, required before
`routes.php` so the routes can use them too:

```php
require __DIR__ . '/../helpers.php';
require __DIR__ . '/../routes.php';
```

```php
// helpers.php
function dump(...$values)
{
    echo '<pre>';
    var_dump(...$values);
    echo '</pre>';
}

function view($viewName, $variables=[]) {
    extract($variables);
    include __DIR__ . "/views/$viewName.php";
}
```

Remember to delete `dump()` from `index.php`, or PHP complains that the function is being
declared twice. And note the **double quotes** around the view path: only double-quoted
strings put the value of `$viewName` into the text.

### 4. 📦 `compact()` and `extract()`

After the move, the pages loaded but the posts were gone. The view is included *inside*
`view()`, and inside that function `$title` and `$posts` do not exist. Variables have to
be handed over somehow, without giving every view the same fixed list of parameters.

Two built-in functions do exactly that, in opposite directions:

- **`compact('title', 'posts')`** packs variables into an array: the keys are the variable
  names, the values are their values.
- **`extract($array)`** unpacks an array back into variables named after its keys.

```php
public function us()
{
    $title = 'U.S';
    $posts = [ ... ];
    view('us', compact('title', 'posts'));
}
```

The default `$variables=[]` lets a view be called with no data at all: `view('form')`.
Extracting an empty array creates nothing and breaks nothing.

### 5. 📝 A first form

A new route, a `form()` method that only shows a view, and a nav link (the unused Design
link became Form):

```php
public function form() {
    view('form');
}
```

```html
<form action="/answer" method="POST">
  <label for="name">Name:</label>
  <input name="name" type="text" id="name" placeholder="Name">
  <label for="age">Age:</label>
  <input name="age" type="number" id="age" placeholder="age">
  <input type="submit" value="Send">
  <input type="reset" value="reset">
  <button>Submit</button>
</form>
```

What each piece is for:

- **`placeholder`**: grey hint text inside an empty field.
- **`<label>`**: the proper caption for a field. It has to be *linked* to its input, either
  by wrapping the input inside the label, or with `for` on the label matching the input's
  `id`. Linked, clicking the label focuses the field. Some CSS frameworks do not like the
  wrapping style, so `for` + `id` is the safer habit.
- **`type`**: text is the default, but `number`, `email`, `color`, `date`, `range` and
  others give the browser a fitting control. Full list:
  <https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input#input_types>
- **Submitting**: a `<button>` inside a form submits it by default. `<input type="submit">`
  does the same, and since an input has no content, its text comes from `value`.
  `type="reset"` clears the form.
- **`name`**: the one attribute that really matters. A field without a `name` is not sent
  at all. `id`, `placeholder` and labels are all optional for sending.

### 6. 🔍 GET, query parameters and `parse_url`

Without `action` and `method`, the form sends itself to the same page with **GET**, and
the result was a **404**. The address bar shows why:

```
/form?name=Test&age=20
```

The data went into the URL as **query parameters**, and the router compared the whole
string, `?` part included, against `/form`. The router should ignore everything after the
path. Instead of searching for the `?` by hand, PHP already has a function that splits a
URL into its parts (scheme, user, password, host, port, path, query, fragment):

```php
public function __construct(private $path)
{
    $this->path = parse_url($this->path, PHP_URL_PATH);
}
```

Docs: <https://www.php.net/manual/en/function.parse-url.php>

The values themselves arrive in the superglobal **`$_GET`**.

### 7. 📮 POST and where the data goes

Two more form attributes:

- **`action`** sends the data to another address. Ours goes to `/answer`, which needed its
  own route and method:

  ```php
  Router::addRoute('/answer', [PublicController::class, 'answer']);
  ```

  ```php
  public function answer(){
      dump($_GET, $_POST);
  }
  ```

- **`method="POST"`** sends the data in the request body instead of the URL. It shows up in
  **`$_POST`**, and `$_GET` stays empty.

When is GET the wrong choice?

- **Passwords and other sensitive data.** The URL stays in the browser history, in server
  logs, in whatever link gets copied.
- **Long text.** URLs have a length limit. Browsers differ (some allow megabytes), but the
  safe minimum to count on is about **2048 characters**, and the server has its own limit
  too. A contact form or an email body does not belong there.

Refreshing a page that was the result of a POST makes the browser ask whether to send the
data again. That warning exists because a POST usually *does* something (adds a row to a
database, sends a message), and doing it twice is often a bug.

## ✅ Takeaways

1. **Controllers hold the actions, `routes.php` stays a list.** Split into several
   controllers as the app grows.
2. **`[Controller::class, 'method']`** plus `new $class()` and `$controller->$method()` is
   how a router calls a non-static method.
3. **Plain helper functions go in `helpers.php`**, required before the routes.
4. **`compact()` packs variables into an array, `extract()` unpacks them** into the view.
5. **A field without `name` is not sent.** Link labels to inputs with `for` + `id`.
6. **GET puts data in the URL (`$_GET`), POST in the body (`$_POST`).** Never GET for
   passwords or long text; `parse_url` keeps query strings out of routing.
