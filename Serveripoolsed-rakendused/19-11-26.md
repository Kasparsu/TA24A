### 1. 🔧 Getting the blog running again

Before the new code, the project had to run on every machine again. On a fresh checkout
Laravel complains about a missing application key (the `.env` file and `php artisan
key:generate` fix that), the database container has to be up, and PHP needs the PDO
driver for MariaDB enabled in `php.ini` (the `extension=` lines, around line 900 of the
file). Then the database is rebuilt with last lesson's command, which also runs the post
seeder:

```bash
php artisan migrate:fresh --seed
```

If the seeder dies on the test user, it is the unique email problem from last time:
either comment the test user out in `DatabaseSeeder` or use `migrate:fresh`, which drops
the old data first.

### 2. 🃏 A post card from DaisyUI

A list of blog posts usually looks like a set of **cards**: a picture, a title, some text,
maybe a button. DaisyUI's card component has exactly that, so its first example went into
a new partial, `resources/views/partials/post-card.blade.php`. The picture is commented
out for now (posts have no images yet, and nobody needed to stare at the shoes from the
example), and the placeholder texts became the post's fields:

```blade
<div class="card bg-base-100 shadow-sm">
    {{-- <figure>
        <img src="https://img.daisyui.com/images/stock/photo-1606107557195-0e29a4b5b4aa.webp" alt="Shoes" />
    </figure> --}}
    <div class="card-body">
        <h2 class="card-title">{{ $post->title }}</h2>
        <p>{{ $post->body }}</p>
        <div class="card-actions justify-end">
            <button class="btn btn-primary">Buy Now</button>
        </div>
    </div>
</div>
```

Why a partial straight away? The card is small now, but it will grow (images, author,
links), and then it is much nicer to have it in its own file than in the middle of the
page. `{{ }}` prints a variable (it is Blade's short form of an escaped `echo`), and since
`$post` is an object, the columns are simply its attributes: `$post->title`,
`$post->body`.

### 3. 📥 Reading the posts in the controller

How did we get data out of the database in our own PHP framework? A database connection,
then a **model** class that represents one table. Laravel is the same
model view controller idea: import the `Post` model in `PublicController`, ask it for the
posts and hand them to the view with `compact`, just like before. At first that was
`Post::all()`; the final version (section 7) looks like this:

```php
use App\Models\Post;
...
public function index() {
    $posts = Post::paginate(20);
    return view('welcome', compact('posts'));
}
```

The view loops over them with Blade's `@foreach` (Blade has the usual control
structures: `@if`, `@for`, `@foreach` and friends) and includes the card partial for each
post. The partial sees the loop variable `$post` without passing it explicitly.

With `Post::all()` the page showed **all 1000 posts**, each with six paragraphs of lorem
ipsum (that is what the factory asked Faker for). Very long cards, very long page.

![Post::all()](https://api.memegen.link/images/ackbar/Post::all()_on_the_front_page/1000_posts,_six_paragraphs_each.png)

### 4. 🔲 Cards side by side: Tailwind grid

The cards stacked under each other, each the full width of the page. DaisyUI has no grid
at all: it offers components, not structure. Bootstrap had its row and column classes,
but here that job belongs to **Tailwind**, which is still installed under DaisyUI. A short
history lesson: page layouts were first done with tables and floats, then came **flexbox**
(`flex`, `flex-direction`, `flex-wrap`, which still has its problems once you want even
gaps), and later CSS got a separate display mode, **grid**, which solves most of those.
Writing a grid by hand in plain CSS is still a bit painful, but Tailwind makes it two
classes:

```blade
<div class="grid grid-cols-4 gap-4">
    @foreach($posts as $post)
        @include('partials.post-card')
    @endforeach
</div>
```

`grid-cols-4` makes four equal columns, `gap-4` puts the same space between them. Grid
can do much more (skipping cells, complex layouts), but this is all the blog needs.

### 5. ✂️ Fewer posts: limit, offset, take and skip

In SQL the answer is well known: `SELECT * FROM posts LIMIT 20`. Laravel's query builder
has the same thing as a method, `Post::limit(20)`. The catch: `all()` gives back results
immediately, but `limit()` does not. A query can have endless pieces chained onto it
(conditions, order, limits), so the builder does not know when we are done. **`get()`** is
the call that says "the query is complete, run it and give me the post objects".

For the next 20 posts SQL has `OFFSET 20`, and the builder has `offset()`. It is worth
knowing the SQL words, because the framework methods imitate SQL even when we no longer
write SQL ourselves. Laravel also offers two shorter, arguably more logical names for the
same thing: **`take()`** instead of `limit()` and **`skip()`** instead of `offset()`.

### 6. 🔢 The `page` parameter: `$_GET` versus `Request`

Hard-coded offsets are no good; the page number should come from the address:
`/?page=1`, `?page=2` and so on. Plain PHP's `$_GET['page']` still works in Laravel, but it
is not recommended. `$_GET` is an ordinary global array, and nothing stops some other code
in the project (or another developer) from overwriting it, after which you spend an
evening hunting for why the parameter has a value nobody sent.

![Superglobals](https://api.memegen.link/images/dwight/Fact:_$__GET_is_a_plain_global_array/Anyone,_anywhere_can_overwrite_it.png)

Laravel reads those values once when the request starts and keeps them in an
**immutable** object: you can read them, but not change them. To get that object, add an
`Illuminate\Http\Request $request` parameter to the controller method. That looks like
magic (who passes it in?), and it is Laravel's **dependency injection**: before calling
`PublicController::index`, Laravel reads the method's signature with **reflection** (code
that reads code), sees that it wants a `Request`, builds one and passes it in. Then
`$request->query('page', 1)` gives the page number, with `1` as the default when the
parameter is missing. The value arrives as a string, so it was cast to `int`.

Then a little maths, with the page size in its own variable so it is easy to change:
page 1 must skip 0 posts, page 2 skips 20, page 3 skips 40. Multiplying the page by 20
gives 20, 40, 60, one page too far, so subtract one first. Without parentheses the first
try was wrong, because multiplication goes before subtraction; with them it works:
`skip(($page - 1) * $perPage)` and `take($perPage)`, then `get()`. Changing `?page=` in
the address now walked through the posts. This is the most ordinary pagination logic
there is, and worth being able to write yourself.

### 7. 📄 `paginate()` and `links()`

Pagination is needed so often that Laravel does all of the above in one call:
**`Post::paginate()`**. It reads the `page` parameter itself and works the same way, with
one difference: the default is **15** posts per page. Fifteen does not fit four columns,
so the argument sets it to 20 (16 would also divide evenly by four).

Typing page numbers into the address bar is not something users enjoy, so the result
also has a **`links()`** method that prints a complete pagination menu:

```blade
{{ $posts->links() }}
```

A fully working pagination with almost no code.

![links()](https://api.memegen.link/images/cmm/$posts--~glinks()_is_a_whole_pagination_menu.png)

The menu is not in our DaisyUI style, though, because Laravel renders it with plain
Tailwind classes. The documentation shared in the chat
(<https://laravel.com/framework/docs/12.x/pagination#customizing-the-pagination-view>)
explains how to change that: either point `links()` at your own view, or **publish**
Laravel's pagination views into the project:

```bash
php artisan vendor:publish --tag=laravel-pagination
```

That copies them from `vendor/` into `resources/views/vendor/pagination/`, where Laravel
will now use our copies. Of the many files (there are Bootstrap versions and others too)
only two matter for us, **`tailwind.blade.php`** (the full menu with page numbers) and
**`simple-tailwind.blade.php`** (only previous and next), so the rest were deleted. Inside
they are ordinary Blade with `$paginator` methods such as `onFirstPage()`,
`previousPageUrl()`, `hasMorePages()` and `nextPageUrl()`, wrapped in long lists of
Tailwind and dark mode classes:

```blade
@if ($paginator->onFirstPage())
    <span class="inline-flex items-center px-4 py-2 text-sm font-medium text-gray-600 bg-white border border-gray-300 cursor-not-allowed leading-5 rounded-md dark:text-gray-300 dark:bg-gray-700 dark:border-gray-600">
        {!! __('pagination.previous') !!}
    </span>
@else
    <a href="{{ $paginator->previousPageUrl() }}" rel="prev" class="...">
```

## ✅ Takeaways

1. **A DaisyUI card makes a good post preview**; put it in its own partial
   (`partials/post-card`) before it grows.
2. **DaisyUI has no grid**: layout is Tailwind's job, `grid grid-cols-4 gap-4`.
3. **Query builder methods mirror SQL**: `limit`/`offset` (or `take`/`skip`), and
   **`get()`** finishes the query and returns the models.
4. **Avoid `$_GET`**: ask for a `Request $request` in the controller method (dependency
   injection via reflection) and read `$request->query('page', 1)`.
5. **Manual pagination** is `skip(($page - 1) * $perPage)->take($perPage)`; mind the
   parentheses.
6. **`Post::paginate(20)` plus `{{ $posts->links() }}`** does it all; the default page
   size is 15.
7. **`php artisan vendor:publish --tag=laravel-pagination`** copies the menu views into
   `resources/views/vendor/pagination/` so we can restyle them (the homework).
