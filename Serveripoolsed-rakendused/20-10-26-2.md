## 🗂️ Topics Covered

> 🚀 For weeks we built our own little framework in plain PHP: a router, controllers,
> models, views, Composer. This lesson switched to the real thing. A fresh **Laravel**
> project called `blog`, a tour of every folder (most of which turn out to be things we
> already wrote ourselves), why `.env` must never reach Git, and a MariaDB container so
> `php artisan migrate` can build the tables for us.

### 1. 🧰 Installing Laravel

The installation guide (<https://laravel.com/framework/docs/installation#installing-php>)
was the starting point. Composer is already installed from last lesson, so the Laravel
installer can be pulled in globally:

```bash
composer global require laravel/installer
```

Laravel needs a few PHP extensions. Several (curl, mbstring, openssl) were already
switched on because Composer needs them, and `pdo_mysql` came with the database work. The
one that tends to be missing is **fileinfo**. Find the active `php.ini` with:

```bash
php --ini
```

On Windows the extensions are there but commented out: remove the `;` in front of
`extension=fileinfo`. On Linux the extension may have to be installed as a package.

Then, in a projects folder that is **not** already inside a Git repo:

```bash
laravel new blog
```

A blog is a simple domain but has enough different data models (posts, users, comments)
to show how things fit together. The installer asks about a **starter kit** (Livewire,
React, Vue and so on). Usually yes, but for now **None**: we want a clean backend to see
how it works before a frontend framework gets wired in. Pest was the testing choice.

The install sits on *Generating optimized autoload files* for a while (the same Composer
autoload step we saw last lesson, just with many more packages). No need to wait: open a
second terminal and open the folder in VS Code already.

![Install](https://api.memegen.link/images/aint-got-time/Generating_optimized_autoload_files.../Opening_VS_Code_in_the_meantime.png)

### 2. 🗂️ The folder tree: `app/` and `bootstrap/`

The tree looks scary at first, but most of it maps onto our own project:

- **`app/`** is our old `src/`: the autoloaded code. `app/Http/Controllers/` holds the
  controllers (empty for now), `app/Models/` the models, with a `User` model already
  there (a bit more involved than ours).
- **`app/Providers/`** is new: *service providers*. `AppServiceProvider` is the place to
  configure how the app or Laravel itself behaves and override defaults. Mostly left
  alone; the docs say when you need it.
- **`bootstrap/`** has nothing to do with the CSS framework. *Bootstrapping* is the code
  that pulls the application together and starts it, like lacing your boots before you
  leave for work. `bootstrap/app.php` wires up routing, middleware and exceptions:

```php
return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
```

![Folders](https://api.memegen.link/images/panik-kalm-panik/A_fresh_Laravel_app_has_129_files/Controllers,_models,_routes,_views:_we_built_those/storage,_bootstrap,_providers....png)

### 3. ⚙️ `config/` and `env()`

We never had a proper config (the database credentials could have gone into one).
Laravel has a whole folder of config files, each just returning an array of keys:

```php
'name' => env('APP_NAME', 'Laravel'),
```

Most values come through **`env()`**: read the setting from the environment, and if it
is not set, use the second argument as the default. Packages add their own config files,
and we can add ours too.

### 4. 🗄️ `database/`: migrations, factories, seeders

Laravel created a SQLite file during the install; it can go, we are using a real database.

When we built the tables for our own project by hand, nothing was saved anywhere: if the
laptop or the Docker container died, the structure was gone. **Migrations** fix that.
Each migration has two methods: `up()` makes a change, `down()` undoes it. Laravel ships
three, for example the users table:

```php
public function up(): void
{
    Schema::create('users', function (Blueprint $table) {
        $table->id();
        $table->string('name');
        $table->string('email')->unique();
        $table->timestamp('email_verified_at')->nullable();
        $table->string('password');
        $table->rememberToken();
        $table->timestamps();
    });
```

```php
public function down(): void
{
    Schema::dropIfExists('users');
    Schema::dropIfExists('password_reset_tokens');
    Schema::dropIfExists('sessions');
}
```

If `up` adds a table, `down` removes it, and the other way round. Git lets you step back
to an earlier commit; migrations give the database the same ability.

- A **factory** describes how to create one model (one row), mostly with fake data:

  ```php
  return [
      'name' => fake()->name(),
      'email' => fake()->unique()->safeEmail(),
      'email_verified_at' => now(),
      'password' => static::$password ??= Hash::make('password'),
      'remember_token' => Str::random(10),
  ];
  ```

- A **seeder** uses factories to fill the database, with initial data or dummy data for
  testing.

### 5. 🌐 `public/`: `index.php`, `.htaccess` and `robots.txt`

`public/index.php` is the entry point, just like ours: load the vendor autoloader and hand
the request to the bootstrapped app. If you feel the need to edit it, you are probably
doing something wrong.

```php
require __DIR__.'/../vendor/autoload.php';

$app = require_once __DIR__.'/../bootstrap/app.php';

$app->handleRequest(Request::capture());
```

**`.htaccess`** configures Apache, a more powerful web server than PHP's development
server. Its last rule says exactly what our own dev server setup said: if the request is
not an existing folder or file, run `index.php`.

```apache
RewriteCond %{REQUEST_FILENAME} !-d
RewriteCond %{REQUEST_FILENAME} !-f
RewriteRule ^ index.php [L]
```

**`robots.txt`** tells crawlers like Google's what they may and may not visit. There is
no magic: well behaved bots honour it, anyone writing their own crawler can ignore it.
And it can backfire: list your secret pages there and a hacker gets a ready map.

![robots.txt](https://api.memegen.link/images/ackbar/robots.txt:_Disallow_~ssecret--admin/First_file_the_hacker_reads.png)

### 6. 🎨 `resources/`, `routes/`, `storage/`, `tests/`, `vendor/`

- **`resources/`**: `css/app.css` already imports Tailwind, `js/app.js` is empty, and
  `views/` is our old `views/` folder. Views are written in **Blade**
  (`welcome.blade.php`), a template language that is nicer than opening and closing PHP
  tags all the time. Without colours in VS Code, install the **Laravel extension pack**.
- **`routes/`**: our `routes.php` became a folder. `web.php` is where the web routes are
  registered, and the format looks exactly like ours (because our router was designed
  after it):

  ```php
  Route::get('/', function () {
      return view('welcome');
  });
  ```

  `console.php` holds command line commands.
- **`storage/`**: like our `uploads`, `storage/app` is for files the app keeps (private
  by default, `public` for files that should be reachable). `storage/framework` is
  Laravel's own: cache, sessions, test results and **compiled views**. Blade is turned
  into plain PHP, and only re-compiled when the view file changes, so pages load fast.
  `storage/logs` holds the error logs.
- **`tests/`**: Pest on top of PHPUnit, with `Unit` and `Feature` examples. Testing has its
  own course, so we will not do much here.
- **`vendor/`**: where Composer puts other people's code, as before.

### 7. 🔐 `.env`: never commit it

The root dotfiles: `.editorconfig` keeps code style (indentation, tabs or spaces, line
endings) per project, and most editors read it. Then **`.env`**, where all those `env()`
calls get their values.

Every operating system has **environment variables** that programs read. But with ten
Laravel projects on one machine we do not want to set system variables that affect them
all, so each project has a `.env` file. Lookup order: is there a system variable with
that name? Use it. If not, is it in `.env`? Use that. Otherwise the default (or null).

`.env` holds the passwords, usernames, access keys and server addresses, so **`.env`
never goes into Git**. "The repo is private" is not enough: it may become public one
day, the company may open source it years after you left, and Git keeps the whole
history even if the file is deleted later. Bots scan every new public commit for keys
and attack the moment they find one. If it happens, close those keys and issue new ones
right away; "it was only up for a few minutes" is no excuse. A real case: leaked keys to
a deployment environment, crypto mining on rented resources overnight, and a bill of
hundreds of thousands in the morning.

What goes into Git is **`.env.example`**: the same keys with harmless default values, no
secrets. Laravel's `.gitignore` already lists `.env`.

![.env](https://api.memegen.link/images/blb/Pushes_.env_to_GitHub_for_two_minutes/Bots_already_mining_crypto_on_his_cloud_account.png)

The rest of the root, briefly: `.gitattributes` tells Git how to handle file types;
`artisan` is Laravel's command line tool (used below); `AGENTS.md` / `CLAUDE.md` and
`boost.json` come from **Laravel Boost**, which makes AI agents' lives easier;
`composer.json` / `composer.lock` and `package.json` / `package-lock.json` as before;
`phpunit.xml` configures the tests; `README.md` is Laravel's default and can be replaced
with your own notes; `vite.config.js` sets up Vite with Laravel's plugin.

### 8. ▶️ Running the app and the first commit

At the end the installer asked which AI agents Boost should set up for (any choice is
fine), then printed the next step. `composer.json` has scripts like npm, so:

```bash
composer run dev
```

starts the development pieces together, including Vite for hot reloading CSS and JS.
It prints two links; ignore the Vite one, the app is at **<http://localhost:8000>**,
where the Laravel welcome page appears.

Nothing had made a Git repository yet, so the clean install went straight into one,
pushed to a new public repo (<https://github.com/Kasparsu/ta24ablog.git>). That way the
generated code is its own commit and everything after it is ours.

### 9. 🐬 MariaDB in Docker and `php artisan migrate`

Laravel has its own tools for services (**Herd**, and **Sail**, a Docker based tool),
but the simplest path is the `docker-compose.yml` from our own PHP project, copied over
with a different database name, a different port (so both can run at once) and a new
volume name:

```yaml
services:
  db:
    image: mariadb
    restart: always
    environment:
      MARIADB_ROOT_PASSWORD: example
      MARIADB_DATABASE: blog
    ports:
      - 33062:3306
    volumes:
      - ta24ablogdata:/var/lib/mysql
volumes:
  ta24ablogdata:
```

`docker compose up -d` (with Docker running first), then a MariaDB connection in DataGrip
on localhost, port 33062: the `blog` database is there and empty.

`config/database.php` has a separate `mariadb` connection, so `.env` switches from SQLite
to it. These values are not secret (the password is already in the compose file), so the
same change goes into `.env.example` to keep it in Git:

```ini
DB_CONNECTION=mariadb
DB_HOST=127.0.0.1
DB_PORT=33062
DB_DATABASE=blog
DB_USERNAME=root
DB_PASSWORD=example
```

Now Laravel can build the structure itself. `php artisan` lists all the Artisan commands;
the one we need is:

```bash
php artisan migrate
```

It runs the migrations, and DataGrip shows the new tables: `users`, `sessions`,
`password_reset_tokens`, `cache`, `jobs` and friends. The compose file and config went
into Git too, so next time we continue from here.

## ✅ Takeaways

1. **`composer global require laravel/installer`, then `laravel new blog`**, after
   enabling the `fileinfo` extension in `php.ini`. No starter kit for now.
2. **Most of the tree is familiar**: `app/` is our `src/`, `routes/web.php` our
   `routes.php`, `resources/views` our views, `public/index.php` our entry point.
3. **Config reads `env()`**: system variable first, then `.env`, then the default.
4. **Never commit `.env`.** Commit `.env.example` with harmless values; a leaked key
   must be revoked at once.
5. **Migrations make the database reproducible**: `up()` does, `down()` undoes, and
   `php artisan migrate` builds the tables.
6. **`composer run dev`** starts the app on `localhost:8000`; MariaDB runs from the same
   kind of `docker-compose.yml` as before, on its own port.
