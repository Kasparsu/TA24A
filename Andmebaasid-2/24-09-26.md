## 🗂️ Topics Covered

> 🎬 The cinema project needs a database. This session was about designing it well, and
> about the layer that sits between your code and that database once the project is real.

### 1. 🎬 The cinema project's database

Before any code: what does a cinema need to store? Films, halls, seats, screenings, tickets
or bookings, users, maybe news or reviews. For every table, ask:

- **What must be unique?** (an email, a seat within a hall)
- **What must never be `null`?** And if something can be `null`, the backend has to handle
  the missing value later.
- **What is it connected to?** A connection is a column that points at another table's
  `id`, and a **foreign key constraint** makes the database refuse values that point at
  nothing.

Constraints are not decoration. Every rule the database enforces is one less way for bad
data to get in, no matter which piece of code writes it.

You do not have to type the SQL by hand. Build the tables in DataGrip and export the
structure: right-click the schema > **SQL Scripts > Generate DDL to Clipboard** (or
**SQL Scripts > SQL Generator** for more options).

### 2. 🧩 Driver, ORM, framework

Three levels of "talking to a database" from code:

| Level | What it gives you |
|---|---|
| **Driver** | A connection. You write SQL strings, send them, get rows back. |
| **ORM** (object-relational mapping) | Tables described as classes, rows as objects. `insert into posts ...` becomes something like creating a `Post` object and saving it. |
| **Framework** | An ORM plus migrations, models, relations, routing and everything around them. |

The example in class was **Prisma** (JavaScript/TypeScript). The term to search for when
you look at other languages is **ORM**.

Why almost nobody writes raw SQL for a whole application today:

- **The editor knows your schema.** A typo in a SQL string is only discovered when the
  database server rejects it. With an ORM, the code already knows which tables and fields
  exist, so mistakes show up earlier and queries get shorter.
- **Relations become easy.** "This user's posts" is one call instead of a hand-written
  join.
- **Dialects stop mattering.** MariaDB, PostgreSQL, SQLite and Oracle all differ in types
  and details. The ORM knows them. You say "string" and it picks the right type for the
  database you are on. Switching databases becomes a config change, not a rewrite. That
  also allows tricks like a throwaway SQLite database for tests.

### 3. 🔁 Migrations, and why the database is not in git

A database lives in binary files. You *could* commit that folder, but git cannot diff
binary files: change one byte and the whole file may look different. So the data folder
does not belong in git.

What does belong in git is the **structure**, written as code. That is what migrations
are:

```php
// a Laravel migration
public function up(): void {
    Schema::create('flights', function (Blueprint $table) {
        $table->id();
        $table->string('name');
        $table->string('airline');
        $table->timestamps();          // created_at + updated_at
    });
}

public function down(): void {
    Schema::drop('flights');
}
```

Every migration has **two directions**: `up` applies the change, `down` undoes it. That
matters on a live site. If an update breaks something, git takes the code back to the old
version in seconds, but the database is already in the new shape. With migrations you roll
the database back too, instead of repairing it by hand while the site is down.

The same ideas exist everywhere, with nearly the same names: Laravel (Eloquent),
AdonisJS (a Laravel-style framework for JavaScript, with its own ORM), ASP.NET (Entity
Framework), React-based full-stack frameworks, and so on. Which one fits *your* project
is this week's homework.

### 4. 🐳 A MariaDB for `learnphp`

The database runs in Docker next to the project:

```yaml
services:
  db:
    image: mariadb
    restart: always
    environment:
      MARIADB_ROOT_PASSWORD: example
      MARIADB_DATABASE: learnphp     # created on the first start
    ports:
      - 33061:3306                   # 33061 on your machine, so it won't clash
    volumes:
      - ta24alearnphpdata:/var/lib/mysql
volumes:
  ta24alearnphpdata:
```

`MARIADB_DATABASE` only takes effect when the volume is created. If the volume already
exists, the database has to be made by hand.

### 5. 🔌 Connecting from PHP with PDO

PHP has two ways in: **mysqli** (MySQL only, which also works with MariaDB since they
share their roots) and **PDO** (PHP Data Objects), one interface for a dozen databases.
We use PDO. The connection code came straight from the w3schools example:

```php
namespace App;

use PDO;
use PDOException;

class DB {
    public function __construct() {
        try {
            $conn = new PDO("mysql:host=localhost:33061;dbname=learnphp", "root", "example");
            $conn->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
            echo "Connected successfully";
        } catch (PDOException $e) {
            echo "Connection failed: " . $e->getMessage();
        }
    }
}
```

Two things to notice:

- **`use PDO;`** Inside `namespace App`, a bare `PDO` means `App\PDO`, which does not exist.
  Either write `\PDO` everywhere or import it once at the top.
- **There is no `mariadb:` driver.** The DSN says `mysql:`, and it works.

A `/test` route in `routes.php` creates a `DB` object, so opening `/test` shows whether the
connection works.

### 6. 💥 Exceptions vs errors

So far we had seen PHP's plain errors: *notices*, *warnings*, *deprecated* ("still works,
won't in a future version") and *fatal* (the script stops). Exceptions came later in PHP,
and their advantage is that **they can be caught**:

```php
try {
    // something that may throw
} catch (PDOException $e) {
    // handle it instead of dying
}
```

A fatal error cannot be handled. An exception can. If nobody catches it, it still ends up
as a fatal error. `ERRMODE_EXCEPTION` tells PDO to throw exceptions instead of failing
quietly.

### 7. ⚙️ `could not find driver`: enabling `pdo_mysql`

The first `/test` said *could not find driver*. Database drivers are PHP **extensions**,
and on Windows most are switched off by default:

1. Find where PHP is installed and turn on file extensions in Explorer.
2. Copy `php.ini-development` to `php.ini` in the same folder (keep the original).
3. Set `extension_dir = "ext"` (around line 700-something).
4. Uncomment `extension=pdo_mysql` (around line 900-something).
5. Restart the PHP server. It only reads `php.ini` on start.

On Linux the extension is usually a separate package (`php-mysql` or similar).

## ✅ Takeaways

1. **Design first**: uniques, `not null`s and foreign keys are rules the database enforces
   for you.
2. **Driver < ORM < framework.** Real projects almost always use an ORM.
3. **Migrations put the structure in git** and can be rolled back. The data folder does
   not go in git.
4. **PDO** talks to MariaDB through the `mysql:` driver. Import it with `use PDO;` inside a
   namespace.
5. **Exceptions can be caught**, fatal errors cannot.
6. **`could not find driver`** means the extension is off in `php.ini`.
