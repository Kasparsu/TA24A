## 🗂️ Topics Covered

> ⚡ Your cinema projects already have migrations and demo data. This short session looked
> at what happens when that data gets big: how long a query takes, and the two everyday
> cures, **indexes** and **caching**. The same demo was shown to the other group as well.

### 1. 🎬 A movies table with a lot of rows

The demo database was deliberately simple: a single movies table with an auto increment
`id`, a title, a description, a director, a release date and a language. Far simpler than
your cinema schemas, but it had **about a million rows** of fake data (Faker style lorem
ipsum, so the "movies" are not real films). DataGrip only shows the first 500 rows, so you
have to jump to the last page to see how much is really there.

The question to the class: what does your front page actually show? Not *all* movies.
The answers: the most popular ones, the ones on in the cinema right now, maybe the newest
20. So the realistic query is "movies ordered by release date, newest first, limit 20",
something your site would ask on every single page load.

### 2. 🧠 Measuring the query

DataGrip shows how long each query took. The first run of that front page query took
about **31 ms**. Running it a few more times gave 12, 8, 7 ms.

Why the difference? The database **remembers** recent work, so the first run of a query is
usually the slowest and repeats are faster. Ask something slightly different (for example
the same query with an offset, i.e. the next page) and it has to do new work again: back
to around 14 to 16 ms.

![Database remembers](https://api.memegen.link/images/remembers/Remember_when_the_same_query_ran_in_31_ms/and_the_second_time_in_7_ms~q.png)

### 3. 🔎 Indexes: an extra sorted list

When you create tables, ask: **which fields will I search or sort by often?** Without
help, the database has to go through the rows itself. It copes with a million rows, but it
is work.

The fix was an **index** on the release date column, in descending order (newest first,
which is what the front page wants). After that:

| | Before the index | After the index |
|---|---|---|
| First run | ~31 ms | ~18 ms |
| Repeated runs | 12, 8, 7 ms | 4 to 5 ms |

**How it works:** the table is kept sorted by its primary key. An index makes the database
keep **one more sorted list**, by that column. Searching sorted data is much faster:
remember the number guessing game, where you halve the range every time instead of trying
every number. That is the search sorted data allows.

**Why not index everything?** Because the speed has a price. Every time a row is inserted
or changed, the database must update every index too, so **writes get slower**. Index
what you really search by.

**Where to look in your project:**

- The `where` (and sort) parts of your queries: what is the front page, a list or a search
  filtering on?
- A search box that searches titles or descriptions.
- Login: the user is looked up by email or username. If that column is already **unique**,
  it already has an index, because unique keys are indexes too. Otherwise add one.
- Most ORMs and frameworks let you declare an index in the migration, so it does not have
  to be clicked together by hand.
- For heavy full text search over large amounts of text there are separate, dedicated
  search tools.

### 4. 🗃️ Caching: ask once, reuse the answer

4 to 5 ms sounds fast, but the demo database had exactly **one user**. In a real system
thousands of requests hit the database at the same time, and the same numbers get much
worse. The cheapest query is the one you do not send.

"The 20 newest movies" is the same answer for everyone. So ask the database once, **store
the answer**, and hand the stored copy to the next visitors. Where to store it:

1. **A file on disk**: "here are the newest 20 movies", saved once and read back.
2. **A table in the database** set aside for cached answers. Still the database, but a
   trivial lookup instead of the real query.
3. **A separate cache store** such as **Redis**.

Nothing says your application must use only one of these, or only one database. Prefer a
setup or library that lets you start with one store and switch to another by changing
configuration.

**How long to keep it?** It depends on how often the data really changes:

- In a cinema, new films usually come out on Thursdays, so the newest movies list can be
  cached for a long time.
- With other data, think about how often it changes and how stale it may be.
- **Even one second can be worth it.** If thousands of users hit the page every second, a
  one second cache turns all those queries into one, and nobody notices data being a
  second old. The exceptions are things like stock or bitcoin prices, where every moment
  counts.

![Caching](https://api.memegen.link/images/rollsafe/The_database_cannot_be_slow/if_it_only_gets_asked_once_per_second.png)

### 5. 🟥 Why Redis and not just MariaDB?

A student asked why use Redis at all. MariaDB, MySQL and PostgreSQL can keep part of
their data in memory, but not all of it and not all the time. **Redis keeps all of its
data in memory** while it runs, which makes it much faster. It is also simpler: no tables,
just keys and values.

Stores built for caching also come with ready-made features, for example an **expiry
time**: save a record and tell Redis to delete it automatically after an hour. That is
exactly what a cache needs.

## ✅ Takeaways

1. **Measure**: DataGrip shows how long each query takes. The first run is usually the
   slowest.
2. **An index keeps an extra sorted list**: searching and sorting by that column gets
   faster (31 ms down to 4 to 5 ms in the demo), inserts and updates get slower.
3. **Index what you search, filter and sort by.** Unique keys are already indexes.
4. **Cache answers that are the same for everyone**: in a file, a table or Redis.
5. **Choose the cache time by how often the data changes.** Even one second helps under
   heavy load.
6. **Redis lives in memory** and can expire records by itself.
