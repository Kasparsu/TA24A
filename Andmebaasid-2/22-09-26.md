## 🗂️ Topics Covered

> 🧱 Last time the database became reachable from outside the container. This time it gets
> a schema that survives, and one you can hand to someone else.

### 1. 💾 Named volumes: why the data was disappearing

```yaml
db:
  image: mariadb
  volumes:
    - ta24alearndbdata:/var/lib/mysql

volumes:
  ta24alearndbdata:
```

A container's own filesystem dies with the container. Rebuild the image, or run
`docker compose down`, and the tables you created by hand are gone, which is exactly the
annoyance that prompted this.

A **named volume** lives outside the container's lifecycle. `/var/lib/mysql` is where
MariaDB keeps its data, so mounting a volume there means the database survives everything
short of deleting the volume itself.

### 2. 📜 The schema as a file

`project.sql` holds the `CREATE TABLE` statements for the project. The point is not that
typing is slow: it is that a schema in a file can be:

- **re-run** on an empty database and give you the same structure every time
- **version controlled**, so a change is a diff someone can read
- **handed over**: a classmate clones the repo and is running the same database in a minute

Creating tables by clicking around in Adminer gives you a database only you have.

### 3. 🔑 Designing the tables

```sql
create table users
(
    id       bigint unsigned auto_increment primary key,
    name     varchar(1024) not null,
    email    varchar(255)  not null,
    password varchar(2048) not null,
    constraint users_pk_2 unique (email)
);

create index users_email_index on users (email);
```

Decisions worth noticing:

- **`bigint unsigned auto_increment`**: ids are never negative, and `bigint` costs
  nothing now but removes a ceiling you would otherwise hit eventually.
- **`not null`** on everything a user genuinely must have. A nullable column is a promise
  that the value is optional; don't make that promise by accident.
- **`unique (email)`**: the database enforces it. Checking in PHP is not enough: two
  simultaneous signups can both pass the check and both insert.
- **`password varchar(2048)`**: you store a *hash*, not a password, and hashes are long.
- **An index on email** because you will look people up by it on every login.

### 4. 🔗 Foreign keys and `ON DELETE CASCADE`

```sql
create table videos
(
    id          bigint unsigned auto_increment primary key,
    title       varchar(2048)   not null,
    user_id     bigint unsigned not null,
    description text            null,
    path        varchar(2048)   not null,
    constraint videos_users_id_fk
        foreign key (user_id) references users (id)
            on delete cascade
);
```

The foreign key makes it **impossible** to store a video whose `user_id` points at nobody.
`ON DELETE CASCADE` then answers the follow-up question: delete a user and their videos go
too, rather than becoming orphans the application has to keep stepping around.

Note `user_id` is `bigint unsigned`: the same type as what it references. A foreign key
between mismatched types is rejected, and that error message is famously unhelpful.

## ✅ Takeaways

1. **Without a named volume your database is temporary.** Mount one at `/var/lib/mysql`.
2. **Keep the schema in a `.sql` file.** Repeatable, reviewable, shareable.
3. **Let the database enforce what must be true**, `not null`, `unique`, foreign keys.
   Application checks alone lose races.
4. **Store hashes, and give the column room.**
5. **Match the types on both sides of a foreign key**, or it will simply refuse.
